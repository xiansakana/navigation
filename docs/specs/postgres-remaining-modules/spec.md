# 剩余四模块迁移 PostgreSQL 规格

状态：待批准
范围：`记账（bookkeeping）`、`实盘组合（portfolio）`、`抄底资金（dip cash）`、`qqq-dip`
基线提交：`9b2c7c7`（生产已切换 RBAC、命理、博客、资源、知识库、Torn、QQ 登录监控、量化）

## 1. 背景与已确认事实

- 生产 `navigation` 库已由 `shared/db/postgres/001-initial.sql` 初始化，并完成 SQLite 基线导入（85 表、1,823,116 行、逐表校验通过），版本行固定为 `001-initial`。
- 现有 PG 模块均采用「异步 repository + 模块级 URL 变量 + 未配置时回退 SQLite」的模式，例如 `portal/src/blog-postgres.js` 与 `portal/src/blog-postgres-runtime.js`。
- 四个待迁模块仍是同步 `better-sqlite3` 调用，且共享数据互相耦合：
  - `portfolio_users`、`portfolio_user_meta`、`investment_accounts`、`investment_account_audit`、`fund_holdings`、`holdings_meta`、`quotes`：被 stock-manage、qqq-dip、portal 记账共同读写。
  - `dip_cash_funds`、`dip_cash_fund_audit`：在组合写入事务内由 `shared/dip-cash-funds.js#applyDipCashRules` 维护。
  - `bookkeeping_*`：portal 记账写入；stock-manage 的账户绑定选项与证券历史价格读写也直接使用。
- 关键调用规模（已核对）：
  - `portal/src/bookkeeping-store.js` 404 行 / 35 处 SQL；`bookkeeping-catalog.js` 156 行 / 38 处；`bookkeeping-asset-history.js` 212 行 / 17 处；`bookkeeping-security-history.js` 153 行 / 9 处；`bookkeeping-qq.js` 192 行 / 26 处；`bookkeeping-import-review.js` 87 行 / 5 处。
  - `shared/investment-accounts.js` 279 行 / 31 处；`shared/dip-cash-funds.js` 98 行；`shared/db/portfolio-store.js` 216 行 / 25 处；`shared/db/portfolio-bridge.js` 271 行。
  - `stock-manage/src/server.js` 890 行，39 个路由/处理器直接依赖同步 store 或同步投资账户函数；`trade-routes.js`、`trade-import-routes.js` 另有 5 个路由。
  - `qqq-dip` 的 store 调用 88 处，集中在 `server.js`（18）、`execution-routes.js`（30）、`monitor.js`（23）、`execution-plan.js`（5）、`execution-defaults.js`（2）。
- `qqq-dip` 未声明 `pg` 依赖；`stock-manage` 已含 `pg@8.23.1`。
- `shared/db/postgres/readiness.js` 的 `SCHEMA_VERSION` 硬编码为 `001-initial`，修改版本会使滚动部署期间旧进程全部不就绪。

## 2. 目标与非目标

目标：

1. 四个模块在设置对应 `NAVIGATION_*_POSTGRES_URL` 时，全部读写 PostgreSQL；未设置时保持现有 SQLite 行为。
2. 现有 HTTP API、页面行为、金额精度（整数分）与权限语义不变。
3. 生产按数据域切换服务，切换后用浏览器逐页验证；SQLite 文件与 `config.json` 不动，可回滚。
4. 事务边界保留：组合写入、记账写入、导入确认在 PG 中原子执行。

非目标：

- 不启用 `NAVIGATION_DATABASE_ENGINE=postgres`，不做全站强制 PG。
- 不重写与数据库无关的计算逻辑（`trades.js`、`bookkeeping-analysis.js`、`bookkeeping-ledger.js`、`playbook.js` 等）。
- 不改变 UI 结构，不做额外功能。

## 3. 总体设计

### 3.1 连接变量

在 `shared/db/postgres/config.js` 的 `DATABASE_NAMES` 新增：

| scope | 变量 | 覆盖模块 |
| --- | --- | --- |
| `bookkeeping` | `NAVIGATION_BOOKKEEPING_POSTGRES_URL` | `bookkeeping_*` 全部表、记账 QQ 绑定、资产历史、汇率历史、证券价格历史 |
| `portfolio` | `NAVIGATION_PORTFOLIO_POSTGRES_URL` | `portfolio_users`、`portfolio_user_meta`、`investment_accounts`、`investment_account_audit`、`fund_holdings`、`holdings_meta`、`quotes`、`trades` 视图数据 |
| `qqqDip` | `NAVIGATION_QQQ_DIP_POSTGRES_URL` | `qqq_dip_state` |

`dip_cash_funds` / `dip_cash_fund_audit` 不单独设变量：它在组合写入事务内维护，必须与 `portfolio` 同库同连接，否则预留更新会与成交扣款脱节。文档明确写成「抄底资金随 portfolio 变量一起切换」。

### 3.2 双后端与异步边界

- 所有新增 repository 方法均为 `async`；SQLite 路径保持同步实现。调用方统一 `await`（`await` 同步值合法）。
- 每个模块提供一个运行时工厂，按 URL 选择后端：
  - `shared/db/portfolio-runtime.js`：`getPortfolioBackend(options)` → PG 或 SQLite，返回组合 store、投资账户、基金持仓、抄底资金方法。
  - `portal/src/bookkeeping-runtime.js`：`getBookkeepingBackend()` → PG 或 SQLite，返回记账 store、catalog、历史/汇率/证券价格/QQ 服务。
  - `qqq-dip/src/store-runtime.js`：`openStore(config)` → PG 或 SQLite state store。
- 连接池复用：同一进程同一 URL 只建一个池，应用名分别为 `navigation-portal`、`navigation-stock-manage`、`navigation-qqq-dip`。
- 就绪检查：已有 `verifyConfiguredPostgres` 覆盖；各服务 `/readyz` 在配置了对应 URL 时额外 `SELECT 1`。

### 3.3 事务与并发

- 组合写入：`db.transaction` 内先 `SELECT data FROM navigation.portfolio_users WHERE user_id=$1 FOR UPDATE`，再加载相关账户/持仓/记账行，纯 JS 计算后一次写回 JSON、账户基线、审计、抄底预留。多个服务同时写同一用户时由行锁串行化。
- 记账写入：单事务内完成账单、退款关联、catalog、设置更新；唯一约束冲突映射为现有中文错误。
- 导入：预览仍在内存；确认阶段在单事务内按现有顺序创建账户/账单，重复 `source_key` 跳过。
- qqq-dip：状态为单行 JSON（`id='default'`），每次变更事务内 `SELECT ... FOR UPDATE` 后整体写回；动作列表仍保留 1000 条上限。

### 3.4 SQLite 回滚

- 不读取 `NAVIGATION_DATABASE_ENGINE`；删除模块 URL 并 `pm2 restart <app> --update-env` 即回滚到 SQLite。
- 切换前对 `data/navigation.db`、`data/qqq-dip.json` 做一致性快照；切换后写入 PG 的数据不会自动回到 SQLite，回滚说明中必须标注这一点。

## 4. Schema 变更

新增 `shared/db/postgres/002-qqq-dip-state.sql`：

```sql
CREATE TABLE IF NOT EXISTS qqq_dip_state (
  id TEXT PRIMARY KEY,
  data TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  _sqlite_rowid bigint GENERATED BY DEFAULT AS IDENTITY UNIQUE
);
```

决策：**不修改 `001-initial.sql`、不提升 `SCHEMA_VERSION`**。原因：

1. `rehearse-postgres.py --baseline` 要求 SQLite 快照与基线表集合完全一致；把 PG 专有表加进 001 会使后续基线导入直接失败。
2. 提升版本会让滚动部署窗口内新旧进程互相判定不就绪。

`002` 是幂等增量脚本，生产与全新初始化的库都在基线导入后执行一次；`docs/postgres-migration.md` 记录执行命令与「PG 专有表不参与 SQLite 基线比对」的约束。

## 6. 切换顺序（生产）

1. 部署新代码，四个 URL 均不设置；确认所有服务 `/readyz` 与页面仍走 SQLite。
2. 备份：服务器上对 `data/navigation.db`、`data/qqq-dip.json` 做时间戳副本。
3. 执行 `002-qqq-dip-state.sql`（幂等）。
4. 组合域（必须同时）：
   - `portal`、`stock-manage`、`qqq-dip` 设置 `NAVIGATION_PORTFOLIO_POSTGRES_URL`；
   - `pm2 restart portal stock-manage qqq-dip --update-env`；
   - 验证组合/现金/抄底预留。
5. 记账域（必须同时）：
   - `portal`、`stock-manage` 设置 `NAVIGATION_BOOKKEEPING_POSTGRES_URL`；
   - `pm2 restart portal stock-manage --update-env`；
   - 验证记账明细、账户、统计、导入。
6. qqq-dip 状态：
   - `qqq-dip` 设置 `NAVIGATION_QQQ_DIP_POSTGRES_URL`；
   - `pm2 restart qqq-dip --update-env`；
   - 验证状态、设置、通知、执行记录。
7. `pm2 save`；`/readyz` 全部 200。

回滚：删除对应变量 → `pm2 restart <app> --update-env` → `pm2 save`。SQLite 文件始终保留；切换后写入 PG 的数据需人工评估是否补回 SQLite。

## 8. 风险与缓解

| 风险 | 缓解 |

| 组合与抄底资金跨服务耦合 | 同一变量、同一批次重启、切换前后对比现金/预留 |
